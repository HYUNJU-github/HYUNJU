
# house-style
> 제안서/공문 서식 규칙. 산출물 생성 시 준수.

## 1. 작성 단위와 기준본

- 제안서: 장(章) 단위 분리 작성. 합본은 마지막에 조립, 중간에 전체 재작성 금지.
- **합본 이후에는 장별 파일로 되돌아가지 않는다.** 통합본이 만들어진 시점부터 그것이 유일한 편집 대상이며, 장별 개별 파일에서 재통합하지 않는다(사용자가 통합본에 직접 가한 조정이 소실되기 때문).
- **기준본(baseline) 규칙**: 사용자가 직접 열어 위치·크기·문구를 조정해 저장한 버전이 기준본이 된다. 이후 모든 수정은 기준본을 복사해 시작하고, 기준본이 바뀔 때마다 DECISIONS.md에 `기준본을 <파일명>으로 갱신` 형식으로 기록한다. STATE.md의 `현재 keeper`에도 반영한다.

## 2. 버전·보관

> **2026-10-29 개정 — 헌법 「판 올리기」에 맞췄다**(사용자 지시 「house-style 을 헌법 맞춰」).

  범위·구조가 바뀌면 `1.0` 단위로 올린다. 덮어쓰면 **누가 어느 판을 보고 답했는지**가 사라진다.

  🪤 **종전 규칙은 「20_output 은 vNN 누적을 허용한다」였고, 2026-10-29 에 뒤집었다.**

  **깨진 v1.5 를 집어 고객에게 보낼 뻔했다**(구축사용이 「학교용 안건 28」을 가리키는데 v1.5 는 27 에서 끝났다).

- **판을 올리면 그 파일을 «가리키는 쪽»도 같은 작업에서 고친다** — INDEX·STATE·생성기 상수·문서 안의 근거 칸.
  살아 있는 포인터는 판을 올리고, **이력 기록은 판을 그대로 두고 경로만 보관으로** 바꾼다(올리면 「그때 그 판」이 거짓이 된다).

- **최종 파일명 규칙** — 구분자를 고정한다. 밑줄만 쓰면 **어디까지가 사업명인지 기계가 못 가른다**

  | **일반 산출물** | `<문서번호>.<문서명>_v<N.N>.<ext>` | `KNUE11_DD_03.질의서(학교용)_v2.1.xlsx` |
  | **반복 산출물**(회의록·주간보고·메일) | `<문서번호>.<문서명>(<회차 또는 회의명>)_<yymmdd>.<ext>` | `KNUE11_PM_20.회의록(프로세스협의)_261029.md` |
  | **외부 입수문서**(`00_context/_raw`) | `<입수일자>_(<입수처>)_<원본파일명>` | `20261029_(서울시립대)_문서작성지침서_V1.4.hwp` |

  다른 회의는 다음 판이 아니라 **다른 문서**다. 날짜로 가른다.
  *(출처: 서울시립대 PMO 문서작성지침서 V1.4 §3.4 — 주간보고·회의록만 날짜형으로 따로 규정한다)*

### 2.1 제출 판은 내부 판과 «다른 축»이다

발주처 지침이 **「승인 단계가 곧 버전」**인 경우가 있다
(실례: 서울시립대 PMO 문서작성지침서 V1.4 §3.2 — V0.7 담당자 작성완료 / V0.8 수행사 PM 검토완료 /
V0.9 PMO 검토완료 / **V1.0 발주기관 승인**).

🔴 **그 숫자를 우리 내부 판에 섞지 마라.** 둘은 같은 기호를 다른 뜻으로 쓴다 —
저쪽은 **상태 표시**, 우리 §2 는 **변경 추적**이다.

- 섞으면 깨지는 것 ① 1인에게 V0.7·V0.8·V0.9 는 같은 순간이라 **0.1~0.6 이 영영 빈다**
  ② 거꾸로 우리 `v0.3` 을 받은 쪽은 **「PM 검토도 안 들어간 미완」**으로 읽는다
  ③ 저쪽 체계에서는 승인 전 수정이 전부 한 파일 안에서 일어나 **덮어쓰기가 정상**이 된다 — 헌법 「판 올리기」가 막는 바로 그것
  ④ 저쪽 표준템플릿 줄은 `V0.07/0.08/0.09/`**`V0.1`** 이라 숫자로 읽으면 **승인이 검토보다 작다.**
     버전이 수가 아니라 **코드**라는 증거다
- **내부 판**(`10_work`·`20_output`): §2 그대로 — 내용 바뀌면 `0.1`, 범위·구조면 `1.0`
- **제출 판**: 제출 시점에만 발주처 번호를 붙여 **사본**으로 만든다. 원본을 리네임하지 않는다
- 만든 즉시 `DECISIONS.md` 에 한 줄 — `제출 V1.0 = 내부 v2.1 (<날짜> <받는 곳>)`.
  **이 한 줄이 「고객이 든 판 ↔ 내가 든 판」을 잇는 유일한 선이다**(§1 기준본 규칙의 확장)

🔑 **V1.0 이후로는 두 체계가 일치한다.** 저 지침서도 V1.1~V1.4 를 내용 변경마다 올렸다.
다른 것은 **V1.0 이전 구간뿐**이다 — 거기서만 조심하면 된다.

## 3. 분량 관리

- 발주처가 정한 분량 상한(본문 N페이지/N장, 요약서 N페이지)을 프로젝트 시작 시 STATE.md·INDEX.md에 상수로 박아둔다.
- **상한에 근접하면 신규 슬라이드를 추가하지 말고 기존 페이지 하단을 보강한다.** 장수를 고정하고 밀도를 올리는 편이 상한 관리와 조견표 페이지 안정성에 유리하다.
- 페이지 배분은 평가 배점에 비례하되 **요구사항 밀도를 반영**한다. 배점이 낮아도 요구사항이 몰린 장은 두껍게 잡는다.

## 4. 내용 규칙

- 표/구성도 우선, 장문 서술 최소화.
- 수치·근거는 산출내역/견적 xlsx와 상호 일치시킬 것.
- **모호한 표현 금지**: "가능하다·할 수 있다·고려하고 있다" 등은 공공 제안서 평가에서 **불가능한 것으로 간주**된다. 계량 가능한 것은 전부 수치로 쓴다.
- 발주기관 지칭 통일(예: "고객사" → "발주기관").

## 5. 평가본 익명화 (공공 제안서 필수)

원본과 별개로 평가본(심사위원용)을 만들 때, 제안사를 식별할 수 있는 정보가 남으면 감점 또는 실격 사유가 된다.

- 제거 대상: 회사명·로고·대표자 성명·직인·주소·연락처 — **본문·도식·표·머리말/꼬리말·이미지 안의 글자까지** 전부.
- **PDF 속성(제목·작성자·회사)도 확인**한다. 파일명에도 회사명을 넣지 않는다.
- 표지는 발주처가 지정한 평가용 표지 양식을 사용한다.
- 익명화 검수는 최종 인쇄 직전에 원본↔평가본을 나란히 놓고 전수 확인한다.

## 6. PDF 제출

- **글꼴 포함(임베딩) 저장**을 기본으로 한다. 제출 PC·심사위원 PC에 KoPub돋움체가 없어도 동일하게 보이게 하기 위함이다.
- 사전배포·심층검토용으로 PDF가 배포될 수 있으므로, 발주처가 허용하는 범위에서 복사방지·출력해상도 등 보안설정을 검토한다.
- 인쇄 조건(양면/단색/컬러 허용 페이지)은 RFP 지시를 그대로 따르고, 컬러 허용 페이지를 STATE.md에 명시한다.

### 7.1 수동 → 단정

| 피할 것 | 쓸 것 |
|---|---|
| 남는다 · 유지된다 · 그대로 쓰인다 | **건재하다 · 계속 작동한다 · 손대지 않는다** |
| 최선 · 노력 · 지향 · 하고자 한다 | **최신 · 확정 · 채택** (검증 가능한 말) |
| 가능하다 · 할 수 있다 | **한다** (단정) |
| 지원한다 · 반영한다 | **제공한다 · 적용한다** |
| 방지한다 · 예방한다 | **차단한다 · 없앤다** |

> 「유지된다」는 저절로 그렇게 되는 것처럼 들린다. 실제로는 **설계로 그렇게 만든 것**이므로 「손대지 않는다」가 사실에 가깝다.
> 「가능하다·할 수 있다」는 §4의 모호 표현 금지와 같은 뿌리다 — 공공 제안서에서 **불가능한 것으로 간주**된다.

### 7.2 블록 제목 — 명사 종결 금지

`~기준 / ~절차 / ~체계 / ~방안 / ~계획 / ~관리 / ~구성`으로 끝나는 제목은 **아무것도 말하지 않는다.**

| ✗ | ✓ |
|---|---|
| 환경별 구성 기준 | 개발·검증·운영 3환경을 분리한다 |
| 보안 점검 체계 | 점검은 분기 1회, 결과는 정례 보고에 |
| AI 품질 정량 지표 및 측정 기준 | Top-3 70% · 출처 90% · 부적절 10% |

### 7.3 키메시지 — 요약 금지, 주장할 것

`~를 제시합니다 / 구성합니다 / 수립합니다`로 끝나면 **요약**이다. 심사위원에게 남는 게 없다.

| ✗ 요약 | ✓ 주장 |
|---|---|
| 무상·유상 경계를 항목 단위로 사전 확정하여 분쟁을 예방합니다 | 무상과 유상의 경계는 운영 중에 다투지 않는다 — 계약 전에 항목 단위로 끝낸다 |
| 인증을 나열에 그치지 않고 매핑하여 제시합니다 | 인증서를 붙이는 대신 어느 절차에서 작동하는지 보인다 |

**길이는 문제가 아니다.** 120자를 넘어도 밀도가 있으면 그대로 둔다.

### 7.4 부정형은 논지일 때만

`~하지 않는다 / ~없이`는 **부정이 곧 주장일 때 오히려 강하다.** 전수 치환하지 말 것.
「개인 학사 데이터가 색인에 **없다**」·「외부 API 호출 **없음**」은 그 자체가 논지다.

### 7.5 수정 시점 — 「페이지를 밀리게 하는가」

요구사항 조견표(요구사항 × 페이지 번호)가 대개 임계경로다. 문안 수정이 면 높이를 바꾸면 페이지가 밀려 조견표를 다시 만들어야 한다.

| 시점 | 대상 | 이유 |
|---|---|---|
| **병합 전 (필수)** | 키메시지 · 본문 어휘 · 블록 내용 | 면 높이 변동 → 페이지 밀림 |
| **합본 후 (안전)** | 블록 제목 · 장 간 어조 통일 | 섹션바 한 줄이라 높이 무관 |

## 8. 여러 세션이 같은 폴더를 쓸 때

Claude Code(로컬)와 Cowork(앱)이 한 프로젝트를 동시에 보는 경우가 있다. 서로의 수정을 덮어쓰면 복구가 어렵다.

1. **착수 전 `10_work/_WORKLOG.md`에 한 줄 등록한다** — `시각 | 세션 | 파일 | 작업 | 진행중`
2. **다른 세션이 「진행중」으로 잡은 파일은 건드리지 않는다**
3. **쓰기 직전에 다시 읽는다.** 오래된 사본 위에 쓰지 않는다
4. **강제 덮어쓰기 금지.** mtime 충돌은 「상대가 고쳤다」는 신호다 — 병합 후 다시 쓴다
5. **버전을 올렸으면 같은 턴에** 정본 표(`_README_정본.md` 등)를 고친다
6. **정본 산출물은 한 번에 한 세션만** 만진다

> 실제 사고 2건 (2026-08-21, uos-ai-major)
> ① Cowork이 「Ⅲ장 v70이 정본」이라 적은 직후 Claude Code가 v71을 만들었다 — 20분 만에 정본 표가 어긋났다
> ② Cowork이 파일을 왕복시키는 동안 사용자 편집이 들어왔고, **낡은 로컬 사본으로 덮어 편집분을 잃었다** — 규칙 3을 스스로 어긴 경우다

**역할 분담의 기준은 「루프가 있느냐」다.** 편집→빌드→검증이 반복되는 작업은 한 세션 안에 두고, 왕복이 한 번이면 나눠도 손해가 없다.

### 8.1 다른 세션에 작업을 지시할 때 — 지시문의 3원칙

지시를 받는 쪽은 **적힌 것만** 한다. 프로젝트 규약에 있어도 지시문에 없으면 일어나지 않는다.

1. **착수 지시와 마감 지시는 짝으로 준다.**
   「착수 전 `_WORKLOG.md`에 점유 줄을 적는다」만 쓰면 「끝나면 완료로 바꾼다」는 일어나지 않는다.
   점유판에 「진행중」만 쌓이고 누가 무엇을 끝냈는지 알 수 없게 된다.
   마감 지시에는 **미완 항목의 표기 방법**까지 정해 준다 — 예: 「완료(§3 미실시)」.

2. **여러 단계를 시킬 때는 단계마다 저장을 명시한다.**
   스캔 → 판정 → 검증 → 보고서를 한 덩어리로 묶으면, 중간에 끊겼을 때 **아무것도 남지 않는다.**
   「1단계가 끝나면 즉시 §1을 파일에 쓰고 그다음으로 간다」로 쪼갠다.

3. **무거운 단계에는 폴백을 준다.**
   전량 렌더·전량 빌드·외부 도구 호출은 실패하거나 시간이 초과될 수 있다.
   그 단계 때문에 **산출물 전체가 막히면 안 된다.** 「실패하면 대상을 줄여 재시도하고,
   그래도 안 되면 해당 절에 사유만 적고 넘어간다」를 미리 적어 둔다.

> 실제 사고 (2026-08-21, uos-ai-major) — 디자인 재검토 지시에서 「점유 줄을 적는다」만 쓰고
> 「완료로 바꾼다」를 빠뜨렸고, 4단계를 한 덩어리로 묶은 데다 전량 회색조 렌더에 폴백이 없었다.
> 결과는 **점유판에 「진행중」만 남고 보고서 파일은 없는 상태**였다. 지시한 쪽의 잘못이다.

**경로는 절대 기준을 밝힌다.** 상대경로를 쓸 때는 기준 디렉터리를 함께 적는다
(예: 「프로젝트 루트 기준 `../_shared/...`」). 받는 쪽의 작업 디렉터리를 가정하지 않는다.

## 9. 디자인은 뱅크·게이트에 종속되지 않는다

배치(박스와 선의 구성)는 **`_shared/templates/제안서디자인_레퍼토리_v1.0.md`가 관리**한다. 색·서체·좌표 규격은 `제안서디자인표준_공유본`이, 문안은 `_shared/bank/`가 관리한다. **세 가지는 서로를 제한하지 않는다.**

1. **레퍼토리는 상한이 아니다.** 카탈로그에 없는 배치를 만드는 것이 레퍼토리의 목적이다. 새로 만들었으면 그 사업이 끝나기 전에 §2에 추가한다.
2. **게이트(`chkdesign.py` G1~G4)는 하한 검사다.** 부품 종류를 채우려고 배치를 바꾸지 않는다 — 내용에 맞는 배치를 고르면 다양성은 결과로 따라온다. G2 밀도 하한에 걸리면 **문안을 늘리는 것이 정답이지 글자 크기를 줄이는 것이 아니다.**
3. **뱅크는 문안 자산이지 디자인 구속이 아니다.** 뱅크에 없는 도해 형태를 만드는 데 허락이 필요 없다. 새 배치가 좋으면 뱅크가 그것을 흡수한다.
4. **외부 제안서·참고 도해는 「규칙에 맞나」가 아니라 「무엇이 좋은가, 무엇을 가져올 수 있나」로 본다.** 규격 검사부터 하면 배치 문법을 놓친다. 규격은 나중에 맞추면 되지만 좋은 구성은 알아보지 못하면 사라진다.
5. **활자 8.0pt가 절대 하한이다.** 양면 100g 인쇄에서 그 이하는 뒷비침과 겹쳐 판독이 무너진다.
   **8.0pt 에 닿으면 선택지는 둘뿐이다 — 내용을 줄이거나, 판을 A3 로 올린다.** 글자를 더 줄이는 길은 없다.
   A3 는 도식·표가 많은 면(프로세스 맵·구성도)에서 **정식 선택지**다(실측 2026-10-29 교원대 프로세스 맵).
   단 **제안서 본문에는 못 쓴다**(분량 상한·제본 규격이 A4 전제). A3 는 **별첨·부속 산출물** 자리다.
   *(출처: 서울시립대 PMO 문서작성지침서 V1.4 §3.1 일반원칙 3 — 「Font Size가 8pt 이하일 경우는 A3활용을 원칙으로 한다」)*
6. **범례가 필요하면 배치가 잘못된 것이다.** 위치·선 종류·명도로 구분되면 범례가 필요 없다.

**흑백 인쇄 사업에서 구분 수단의 우선순위** — 위치 > 선 종류(실선/점선/파선) > 선 굵기 > 명도 > 배지·기호 > **색상은 쓰지 않는다**. 도해 완성 후 회색조로 변환해 실제 판독을 확인한다.

## 10. 기존 제안서 재사용 — 착수 시 필수 절차

**기존 제안서는 회사 표준이다. 새 사업마다 처음부터 쓰지 않는다.**
다만 「감으로 비슷한 면 찾기」는 금지한다 — 틀린 면을 가져오거나 이미 있는 내용을 중복으로 넣는다.

절차는 `_shared/제안서_교차분석_방법론_v1.0.md`를 따른다. 요지만 옮기면:

1. **요구사항 코드로 짝짓는다** — 어휘 유사도로 면을 직접 비교하지 않는다.
   `우리 면 ← 우리 요구사항 ←(대조)← 참고 요구사항 ←(참고 조견표)← 참고 면`
2. **분류 체계 대조표를 먼저 만든다.** 우리에만 있는 분류가 몇 건인지가 재사용 가능 범위다
3. 도구: `python3 _shared/lib/bank/xref.py --ours-xlsx … --ours-deck … --ref-corpus … --out …`
4. **도구는 후보만 낸다.** 정량평가 직결·RFP 원문 대조로 정정한 내용·사업조건이 다른 면은 제외한다
5. 이식은 **면 단위 교체**다 — 크롬은 우리 것, 밴드는 통째, Key Message는 텍스트만
6. 이식 후 **타 발주처 흔적 전수 검사 + 이식 면 렌더 육안 확인**(로고는 텍스트 검색에 안 걸린다)

> **★ 기존 제안서·문안뱅크는 「검증된 것」이 아니라 「전에 쓴 것」이다.**
> 법령·귀속·요율·의무 조항은 반드시 **이번 RFP 원문과 대조**한 뒤 쓴다.
> 2026-08 서울시립대에서 뱅크의 지식재산권 문안(「발주기관 귀속」)이 RFP(「공동소유·지분 균등」)와
> 어긋나, 그대로 썼으면 법이 주는 지분을 문서로 포기할 뻔했다. 틀린 게 나오면 **뱅크를 고쳐 환류**한다.

> **3-gram 반영률로 커버리지를 판단하지 않는다.** 그건 「같은 표현인가」를 재는 지표다.
> 개조식 덱과 서술형 문안은 같은 내용이어도 35% 안팎으로 나온다.

## 11. 문서번호 — 파일이 폴더 밖으로 나갈 때를 위한 것

폴더 슬러그(`P-2026-07-knue-practicum`)는 **파일명에 안 따라간다.**
메일 첨부·Jira 업로드·고객 공유 폴더로 나가는 순간 **어느 사업 것인지 사라진다.**
동시에 스무 건을 돌리는 상황에서 이게 가장 먼저 깨진다.

`<프로젝트코드><단계><차년도>_<문서코드>_<일련번호>`

| 자리 | 규칙 | 예 |
|---|---|---|
| 프로젝트코드 | 폴더 슬러그의 기관약칭 **대문자** | `knue` → `KNUE` |
| 단계·차년도 | 단계 1자리 + 차년도 1자리. 단년·단계 없으면 `11` | `11` |
| 문서코드 | 아래 6종 | `DD` |
| 일련번호 | 문서종류 안의 2자리 일련번호 | `03` |

| 코드 | 뜻 | 우리 산출물 예 |
|---|---|---|
| `PM` | 프로젝트 관리 — 제안서·계획서·회의록·보고서·질의서 | 제안서, 회의록, 주간보고 |
| `AD` | 분석 — 요구사항·프로세스 | 요구사항 xlsx, 프로세스정의서 |
| `DD` | 설계 — 화면·테이블·아키텍처 | 시나리오설계서, 화면관계도, 엔진규칙표 |
| `ID` | 구현 | 공수산정서, 산출내역서 |
| `TD` | 시험·전환 | 시험계획서, 전환계획서 |
| `CD` | 안정화 | 운영 인계서 |

> 출처: 서울시립대 PMO 문서작성지침서 V1.4 §3.3(거기 프로젝트코드는 `UOS11` = 1단계·1차년도).
> **자유 서술 문서종류는 정렬이 안 된다** — 코드를 앞에 붙이면 폴더가 방법론 순서로 선다.
> 번호 대장은 프로젝트 `INDEX.md` 에 둔다. 일련번호를 **재사용하지 않는다**(폐기해도 비워 둔다).

## 12. 산출물은 혼자 나간다

### 12.1 개정이력은 «문서 안»에 둔다

`DECISIONS.md` 는 프로젝트 폴더 안에 있고 **고객이 받은 파일 한 장에는 안 따라간다.**
받는 쪽은 v1.6 에서 v2.1 사이 무엇이 바뀌었는지 **알 길이 없다.**

- **xlsx**: 첫 시트를 `개정이력` 으로. 열은 `판 | 날짜 | 바뀐 것 | 작성` 네 개
- **md**: 머리글 바로 아래 같은 표
- **pptx**: 표지 다음 장(제출본에만). 분량 상한에 걸리면 **표지 하단 한 줄**로 줄인다
- 적는 것은 **「무엇이 바뀌었나」**이지 「고쳤음」이 아니다
  *(형식 출처: 같은 지침서 개정이력 — 「쪽 번호 매기기 원칙 추가(2 페이지)」처럼 **쪽까지** 적는다)*

### 12.2 보안등급을 매긴다 — 캐비닛은 못 해도 분류는 한다

| 등급 | 무엇 | 어디 두나 | 밖으로 |
|---|---|---|---|
| **일반** | 공개 자료·일반 양식 | 아무 데나 | 자유 |
| **대외비** | 설계·산출내역·견적·고객 회신 | 프로젝트 폴더 | **내보낸 기록을 `DECISIONS.md` 에 한 줄** |
| **기밀** | 개인정보 포함 · 발주처가 준 원본 자료 · 자격증명 | `00_context/_raw`(git 제외) | **반출 금지.** 샘플·마스킹본만 |

- 등급은 **파일을 만들 때** 정한다. 나중에는 안 매긴다
- 🔴 **기밀은 세션·로그·커밋 어디에도 값을 올리지 않는다**(헌법 「깨면 안 되는 규칙」 2 와 같은 줄)

> 「시건 캐비닛·세단기·용역책임자 반출승인」은 물리 사무실 전제라 **버렸다** — 남긴 것은 **분류와 기록**뿐이다.
